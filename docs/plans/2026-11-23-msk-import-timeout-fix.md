# MSK 导入恢复测试超时：诊断与修复

日期：2026-11-23。接续 [删除后重置修复与 QA](2026-11-23-msk-delete-reset-fix-qa.md) 中全量测试剩余的超时。范围为测试执行成本，不修改产品页面、接口、主题、路由或权限。

结果：同条件全量组件测试 273/273、全量 Browser Mode 4/4 通过；前后完整数据快照一致，残留测试账号为 0。

## Debug Summary

**问题**：`recovers by reading without repeating an import (write confirmed: false)` 单独运行可通过，在上一轮整份文件及单 worker 全量运行中超过原有 15 秒限制。上一轮最后全量为 272/273，通过后单独复跑不能证明整套已修复。

**根因**：测试在导入弹窗中操作，却使用整页 `screen.getByRole` 计算所有候选按钮的可访问名称；尤其在 `waitFor` 轮询中反复执行这一同步工作。上传文件导致 DOM/样式变化，jsdom 的 CSS 选择器匹配及计算样式占用主线程，既推迟异步状态更新，也使按钮查找本身耗时。多个昂贵定位叠加后，测试体已逼近 15 秒，调度波动即可触发超时。

证据来自当前 checkout 的真实 Rstest 运行与本机 CPU 采样，不把源码猜测当作原因：

- 未修改定位方式时，测试体分段计时为 **13.356 秒**；第一条分支开始时只有 3 个 DOM 节点、0 个样式标签，证明该慢路径不要求前序测试残留。
- 选择文件后等待“导入账号”可用耗时 **4.826 秒**；随后整页定位“查询账号”耗时 **2.764 秒**。
- 点击导入后错误反馈出现仅 **41 毫秒**；该分支使用立即抛错的本地 Axios 适配器，没有真实网络请求等待。
- 整份列表测试的 CPU 采样覆盖约 117 秒：`queryAllByRole` 调用链占 **87.2%**，其中 `getComputedStyle` 调用链占 **63.7%**，DOM 选择器调用链占 **81.9%**。这些为相互包含的调用链占比，不能相加。
- 本地依赖代码 `@testing-library/dom/dist/queries/role.js` 先枚举候选角色，再逐个计算可访问名称与可见性；`dom-accessibility-api` 会为此调用 `getComputedStyle`，和采样栈一致。
- 两个恢复分支的错误/读取适配逻辑没有修改；不存在为通过测试而改成成功响应的操作。

本轮新采样时整份旧定位文件也有一次 14/14 通过，因此超时是有性能证据的间歇问题，不能描述为每次必现。上一轮失败日志、这次未修复的分段计时以及修复后同条件测量共同构成前后证据。

**修复**：仅修改 `src/pages/templates/msk-account-management/msk-account-list-page.test.tsx` 中两处导入测试（合计成功、结果未确认、写入已确认但读取失败三种场景）：

1. 通过 `within(screen.getByRole('dialog'))` 将弹窗内按钮定位限定在实际弹窗。
2. 文件选择前定位一次“导入账号”，明确断言初始禁用，再等待同一按钮启用并点击。轮询中不再扫描整页角色。
3. “查询账号”也在该弹窗内定位。恢复后的列表查询、导入次数、真实处理统计断言保留。

没有提高单项超时、降低断言、修改全局 Testing Library 可见性规则、mock 计算样式或调整测试池配置。全量运行使用的单 worker 参数与上一轮 272/273 的运行相同，方便直接比较。

**验证边界**：这些组件测试覆盖文件选择、显式提交、错误展示、读取恢复及“不重复导入”。它们不能替代真实后端导入落库或浏览器布局验收。本轮没有产品代码或界面文案变动。

**预防**：保留原有 15 秒限制和行为断言，新增初始禁用断言；通过局部查询与稳定 DOM 引用消除轮询重复扫描。未新增时间敏感的性能断言或常驻诊断日志。

**信心**：高。分段计时、CPU 栈及改变定位范围后的耗时下降相互印证。
